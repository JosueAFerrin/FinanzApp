# Desarrollo de aplicación de control financiero personal — PWA

Quiero que desarrolles desde cero una aplicación web de **control financiero personal**, diseñada para funcionar tanto en **computadores como en celulares**. La aplicación debe ser una **Progressive Web App (PWA)**, responsive, instalable en dispositivos móviles y usable desde cualquier navegador moderno.

## 1. Objetivo de la aplicación

La aplicación permitirá a cada usuario administrar sus finanzas personales, registrando y analizando:

* Ingresos.
* Egresos.
* Gastos fijos.
* Gastos variables.
* Fuentes/categorías de ingresos.
* Fuentes/categorías de egresos.
* Ahorro mensual.
* Ahorro anual.
* Resúmenes financieros mensuales y anuales.
* Gráficos y estadísticas de comportamiento financiero.

Cada cuenta debe tener sus propios datos completamente aislados de los demás usuarios.

---

# 2. Antes de programar

Antes de escribir código:

1. Analiza los requerimientos.
2. Propón una arquitectura completa y justifica brevemente las decisiones.
3. Selecciona el stack tecnológico más conveniente considerando:

   * Desarrollo moderno.
   * Mantenibilidad.
   * Seguridad.
   * Buen rendimiento.
   * PWA.
   * Facilidad de deployment.
   * Herramientas gratuitas o con free tier.
4. Define la estructura de carpetas.
5. Define el modelo de datos y sus relaciones.
6. Define los endpoints/API necesarios.
7. Define las reglas de autorización y seguridad.
8. Define las principales pantallas y flujo de navegación.
9. Presenta este diseño antes de comenzar la implementación.

No quiero que agregues tecnologías innecesarias. Prioriza una arquitectura sencilla, profesional y fácil de mantener.

---

* Neon.

La base de datos debe permitir:

* Usuarios.

* Categorías.

* Gastos variables.
* Registros mensuales.
* Consultas agregadas para reportes.

Si utilizas Supabase, aprovecha correctamente Row Level Security (RLS) para garantizar el aislamiento de los datos entre usuarios.

Debe incluir tarjetas/resúmenes como:

* Ingresos del mes.
* Egresos del mes.
* Ahorro del mes.
* Porcentaje de ahorro.
* Gastos fijos.
* Gastos variables.

Ejemplo:

Ingresos:
$2,000

Egresos:
$1,250

Ahorro:
$750

Porcentaje de ahorro:
37.5%

---

# 8. Cálculo del ahorro

El sistema debe calcular automáticamente:

### Ahorro mensual

`Ingresos del mes - Egresos del mes`

### Ahorro anual

`Ingresos del año - Egresos del año`

También calcular:

### Porcentaje de ahorro

`(Ahorro / Ingresos) * 100`

Controlar correctamente casos como:

* No existen ingresos.
* No existen gastos.
* El usuario tiene más gastos que ingresos.
* Valores negativos.
* Meses sin registros.

No generar errores por división entre cero.

# 9. Reportes y gráficos

Crear una sección específica de reportes.

Debe existir una visualización mediante **gráfico de líneas** para observar la evolución financiera.

Como mínimo:

### Reporte mensual

Mostrar por mes:

* Ingresos.
* Egresos.
* Ahorro.

Permitir seleccionar el año.

Ejemplo:

Enero → ingresos / egresos / ahorro
Febrero → ingresos / egresos / ahorro
Marzo → ingresos / egresos / ahorro
etc.

### Reporte anual

Mostrar la evolución de los años disponibles.

Permitir comparar:

* Ingresos anuales.
* Egresos anuales.
* Ahorro anual.

También sería útil incluir gráficos adicionales si aportan valor UX, por ejemplo:

* Distribución de gastos por categoría.
* Gastos fijos vs variables.
* Distribución de ingresos por fuente.

No sobrecargues la interfaz con gráficos innecesarios.

# 13. Seguridad

Este punto es MUY importante.

Implementa las mejores prácticas de seguridad apropiadas para una aplicación web moderna.

Como mínimo:

* Validación de inputs en frontend y backend.
* Sanitización cuando sea necesaria.
* Protección contra SQL Injection.
* Protección contra XSS.
* Protección contra CSRF cuando aplique.
* Protección contra ataques de autenticación.
* Password hashing seguro si administras las contraseñas directamente.
* Cookies seguras cuando sean utilizadas.
* `HttpOnly`.
* `Secure`.
* `SameSite`.
* Control de sesiones.
* Rate limiting en endpoints sensibles.
* No exponer secretos en el frontend.
* Variables de entorno para credenciales.
* No almacenar contraseñas en texto plano.
* No almacenar tokens sensibles de forma insegura.
* Validación de autorización en servidor.
* Principio de mínimo privilegio.
* Headers de seguridad.
* CORS correctamente configurado cuando aplique.
* Manejo seguro de errores.
* No devolver stack traces al usuario.
* Logs sin información sensible.
* Protección de endpoints.
* Dependencias actualizadas y sin vulnerabilidades conocidas.

Utiliza herramientas como:

* Zod para validación, si aplica.
* ORM seguro como Prisma/Drizzle, si aplica.
* Dependabot/npm audit u otra alternativa para revisar dependencias.

Si utilizas Supabase/PostgreSQL, configura correctamente las políticas de seguridad/RLS.

IMPORTANTE:

No quiero una aplicación que simplemente oculte datos en el frontend. La seguridad y autorización deben existir realmente en el backend/base de datos.

Si encuentras una decisión de arquitectura que pueda afectar:

* seguridad,
* escalabilidad,
* costos,
* mantenimiento,
